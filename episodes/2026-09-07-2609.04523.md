MaxKernel: Agentic Kernel Generation for TPUs, by Shangkun Wang, Nina Cai, and Charles Hong, from Google and Google DeepMind. The paper presents a multi-agent system for automating TPU kernel engineering, benchmarked on JAXBench, a suite of 50 diverse kernel tasks built from real workloads of state-of-the-art open-source models, plus production kernels where hand-tuned references exist. The headline numbers: a 1.58 times geometric mean speedup across the full JAXBench workloads, and on the eight production kernels with human-written baselines, a 2.32 times geometric mean speedup for the best agent configuration against 2.02 times for the human hand-tuned code. The framework is released as open source under the accelerator-agents repository.

The motivation is that TPU kernel work is painstakingly manual. Accelerator APIs are rigid, memory constraints are strict, compiler errors are opaque, and even functionally correct code needs iterative empirical profiling to reach peak performance. Compiler frameworks like Halide, TVM, and Ansor decouple algorithms from scheduling but still demand domain expertise or expensive evolutionary search. LLM-based approaches help, but standard zero-shot or few-shot generation falls short without real-time compiler feedback and profiling in the loop.
The architecture is a shared pool of specialized sub-agents orchestrated three different ways. The sub-agents are: a planning agent that writes a high-level algorithmic optimization plan from the hardware specs and the reference implementation; an implementation agent that translates the plan into valid Pallas code, with an iterative compile-fix loop that interprets compiler feedback and resolves errors before execution; a test synthesis agent that builds test suites and an execution agent that runs them on the target hardware against the reference implementation with dynamically specified numerical tolerances per TPU generation; an autotuning agent that explores block sizes and tile dimensions; and a profiling agent that pulls XProf traces and extracts latency, memory bandwidth utilization, and compute density as actionable feedback for the next iteration. The knowledge store is a RAG pipeline over static sources only, framework documentation, memory layout guides, and performance handbooks for Pallas, Mosaic, and XLA. The deliberate design choice is to exclude hand-tuned kernel code from the retrieval corpus, because the point is to measure how much the agents can discover TPU-specific optimizations without reading human-engineered solutions.

The three orchestration paradigms trade control for breadth. Human-in-the-Loop follows a one-agent-then-wait pattern where an orchestrator router keeps the developer in control at critical decision points, which is the mode for complex kernels where architectural alignment matters. The Autonomous Loop is a closed loop of planning, generation, testing, and trace-based profiling with no human in the middle. Graph-Based Autonomous Search extends the loop by modeling the kernel design space as a formal search graph and running search algorithms over it, the paper evaluates two: a simple parallel search that allocates a deep refinement budget of five sequential iterations to independent trajectories, and a beam search that keeps a shallower budget of two iterations per depth before pruning and pivoting. The progression curves the authors plot tell a clean story: parallel search, with its longer per-trajectory budget, climbs steadily as it iteratively debugs compilation errors and matures memory layouts, while beam search climbs in the first two depths and then plateaus, because low-level kernel optimization in Pallas is brittle, and the shallow budget can penalize bold multi-step optimizations that need a longer horizon to resolve rigid memory constraints. Beam search still wins in spaces with many easily-compilable local minima, where breadth and diversity of top candidates matter more than long refinement.
The production-kernel results are the strongest part of the evaluation, and they are workload-level, which is more convincing than a single aggregate. On eight production kernels where hand-tuned Pallas references exist, the parallel search configuration hits a 2.32 times geometric mean speedup over the JAX/XLA reference code, against 2.02 times for the human hand-tuned kernels, and it beats the human code on seven of the eight workloads. The standout is Paged Attention, where beam search found a 6.74 times speedup kernel, more than double the hand-tuned reference of 2.41. The one exception is Ragged Paged Attention, where the human expert's 4.65 times beats the agent's 1.42 times, so this is not a uniform win. On the full JAXBench suite of 50 tasks, the geometric mean speedup is 1.58 times, with a floor of 1 times applied in the aggregation, meaning some workloads did not improve at all. Beyond speedups, the system was also used for robustness: on the Multi-Head Latent Attention v1 architecture it cut latency by 8.68 percent and raised throughput by 9.50 percent over the human Pallas baseline, on Qwen3-Next Gated DeltaNet it cut forward latency by 1.63 times and accelerated the full training step by up to 4.70 times, and on DeepSeek-V4 Sparse Attention it beat the JAX baseline across all shape configurations from 2.36 times on small decoding shapes to 7.85 times on prefill. It also fixed real bugs, adding protective ALU clamp instructions in the Ragged Page Attention v3 prefill path to handle left-padded inputs without negative slice sizes.

My assessment: the core claim, that a closed loop of compiler feedback and hardware profiling lets agents match and often beat hand-tuned TPU kernels, is well supported, and the experimental design, especially excluding human kernel code from the RAG corpus and reporting per-workload rather than only aggregate numbers, is more careful than most agentic-code-generation papers. What I would re-verify before betting on it: the JAXBench speedups are against the JAX/XLA reference, which is a strong but not the ceiling baseline, so the 1.58 times headline overstates the gap to a fully optimized stack; the evaluation is TPU and Pallas specific, and the authors' own claim that the principles port to other accelerators is untested in this paper; and the human comparison is only eight kernels, so the seven-out-of-eight result is directionally interesting but a small sample. If you are writing TPU kernels today, this is one of the more directly useful agentic systems released this year, and the open-sourced agent with its search-graph mode is a reasonable thing to point at your own workloads. If your stack is not TPU, treat it as a design template for closed-loop kernel agents rather than a turnkey tool.
The autonomous loop has several engineering details worth copying, because they address failure modes that agentic coding papers usually wave away. Before the loop starts, the test suite is synthesized from the reference code and then frozen, explicitly so that downstream implementation agents cannot reward-hack the validation criteria to pass correctness checks artificially. The loop itself is a strict sequence: plan generation, implementation, compilation validation, test execution, autotuning, and profiling, with the empirical profiling feedback from the final stage fed directly into the planning phase of the next iteration. When a hard failure happens, like hitting the compilation retry limit or a numerical correctness check failing, the pipeline short-circuits, preserves the error context, and loops back to planning for an alternative strategy rather than grinding on a dead end. The orchestrator also maintains a snapshot history of every successful iteration, recording code, compile status, test results, latency, and profiling summaries, and at the end it rolls the workspace back to the lowest-latency valid solution, so a regression in iteration eight cannot ship. And to keep the loop deterministic, the root agent dictates absolute file paths for every artifact at initialization and injects those into the sub-agent prompts, which prevents the state corruption that comes from agents inventing their own file layouts mid-run. The graph-based search builds on this by making each node a full kernel state, code, plan, and metrics, and by isolating each node expansion into a separate agent session, which is a clean way to keep LLM context windows from overflowing as the search deepens, and the persistent graph state also means the search can resume after an unexpected halt.
