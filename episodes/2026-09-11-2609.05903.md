Good evening, welcome back to Papercast. I'm your host, and tonight's third paper is EvoSafeHarness, from Nanxi Li, Yingzi Ma, and Yulong Cao, with the team spanning Johns Hopkins University, NVIDIA, the University of Illinois at Urbana-Champaign, and UC Berkeley. This is an agent safety paper, and it is a good example of where this subfield is heading: instead of patching the model, the authors build and evolve a custom safety harness around it. The harness is the wrapper system, the policies and the code that sits between the user's request and the model's actions.

The problem, in one sentence: large language model agents are increasingly given access to real tools, emails, files, browsers, and accounts, and that access makes them exposed to two kinds of threats. The first is indirect prompt injection, where a malicious instruction is hidden inside some document or webpage the agent is supposed to read, and the agent obeys it as if the user had asked. The second is direct harmful requests, where the user themselves asks the agent to do something unsafe. The standard response to both is to add guardrails, but most guardrails are generic, hand-written rules that either block too much and hurt the agent's usefulness, or are tuned to one specific benchmark and fail when the deployment changes. There is also a practical asymmetry that the paper leans on: the model's weights are often frozen at deployment time. The organization running the agent usually did not train the model, and retraining a frontier model to be safer is not an option available to them. That means the practical place to put safety work is the wrapper, and that is exactly where EvoSafeHarness lives.

EvoSafeHarness's answer is to treat the harness as something to be optimized, not hand-crafted. The system takes a frozen model, a model whose weights you are not going to touch, and a target domain, say, an email agent or a web-browsing agent. It then runs an evolutionary search over two things at once: natural-language policies, which are written instructions the agent follows, and executable code logic, which is actual programmatic checks that can inspect the agent's state and block or rewrite actions. The search is guided by three signals. It looks at the model's own behavior, it respects domain specifications, and it runs a fresh-context adversarial review, a separate model call whose only job is to attack the proposed rules and find cases where they are benchmark-specific or too brittle. That adversarial reviewer is a nice touch, because it pushes the evolved harness away from overfitting to the particular benchmark it was trained on.

The search is population-based in the classic evolutionary sense. A set of candidate harnesses is initialized, each is evaluated on a held-out mix of benign and malicious agent traces, the fitter candidates are recombined and mutated, and the process iterates until the safety-utility trade-off stops improving. Two design choices make this more than a generic prompt-rewriter. First, the fitness function is Pareto-aware: a candidate that is perfectly safe but blocks every benign request scores no better than a useless one, so the search is pushed toward the operating point where the agent is both protected and still useful. Second, the natural-language policies and the executable code are co-evolved as a unit. A rule that says to check something is paired with the code that actually performs the check, and the pair is scored together. That pairing is what lets the harness do things a pure prompt-layer guardrail cannot, like inspecting the agent's tool-call arguments, validating a file path against a whitelist, or rewriting a URL before it is fetched. The co-evolution matters most in the code branch: a hand-written allowlist is brittle, but an evolved one has actually seen the failure modes of the frozen model in that domain, so it blocks the specific patterns that leak through rather than a generic blocklist that is either too broad or too narrow.

The results are the strongest part of the paper. On DecodingTrust-Agent, a benchmark of indirect prompt injection attacks against agents, the average attack success rate drops from 45.6 percent to 10.0 percent, and the authors report this at a cost of only about 3.3 points of utility. In plain terms: the agent blocks the vast majority of the injected instructions while still being able to do most of the legitimate tasks it was built for. They report the best score in 14 out of 15 cells in that benchmark's breakdown, which is a very clean sweep.

On AgentDojo, a different and fairly demanding agent benchmark, the harness reaches 82.8 percent utility while holding the attack success rate to 0.0 percent, and the authors note that this is roughly twice the utility of CaMeL, a well-known agent isolation architecture, at the same operating point. Even better for the paper's generalization claim: the harness trained on the seen AgentDojo suites transfers unchanged to the unseen AgentDyn suites, meaning the evolved policies did not just memorize the test. On Agent-SafetyBench, it is the best-scoring method for every victim model they test. And under adaptive attacks, where the attacker sees the defense and refines their injection, they use the PAIR attack method with a refinement budget of 16, and the harness keeps the average attack success rate below 20 percent.

Now the skeptical read, because security results are exactly where I slow down. The first caveat is the attacker budget. Every number here assumes a specific attack model and a specific amount of compute the attacker gets to spend. The adaptive PAIR result is the most honest number in the table, and it is the one to focus on: below 20 percent, not zero. Security in agents is an arms race, and a harness that holds a 16-shot adaptive attack today may not hold a 160-shot attack next quarter. The second caveat is domain coverage. The harness is evolved per domain, which is a feature, but it also means every new deployment is a new optimization run, and the paper does not tell us how expensive those runs are or how stable they are across re-runs. If the evolved harness is sensitive to the random seed or to the exact set of attacks it saw during evolution, then the 0.0 percent number on AgentDojo is a property of that particular run, not a guaranteed property of the method. The third caveat is the classic one for this area: the benchmarks are a proxy for real deployment, and real deployments have more attack surface, more weird documents, and more users trying to jailbreak the system than any benchmark does.

What I find most useful about this line of work, and EvoSafeHarness is a good instance of it, is the conceptual shift. For a while, the dominant instinct was to make the model itself safer, with more alignment training. But a model deployed in a harness with tools is only as safe as the harness, and the model's weights are often frozen by the time the integrator is doing the deployment. Optimizing the wrapper, especially with an adversarial reviewer in the loop, is arguably where the practical safety work is going to happen for a long time, and this is a credible data point for that thesis.

Two-sentence verdict. EvoSafeHarness is a well-executed demonstration that evolved, domain-specific safety harnesses can cut agent attack success rates dramatically, from 45.6 percent to 10.0 percent on DecodingTrust-Agent at a small utility cost, and transfer to unseen suites. The honest limits are the bounded attacker budgets and the per-domain cost of evolution, so treat this as a strong step in an arms race, not a solved problem.
